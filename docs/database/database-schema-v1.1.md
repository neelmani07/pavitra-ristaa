# Pavitra Ristaa — Database Schema v1.1

**MVP:** Dating/Love + Friendship + Marriage  
**Database:** PostgreSQL  
**Tables:** 52  
**Status:** Approved implementation baseline; no Flyway/JPA implementation details in this document.

## Global conventions
- Primary keys use BIGINT GENERATED BY DEFAULT AS IDENTITY.
- Externally exposed business entities use UUID where appropriate; internal BIGINT IDs remain internal.
- All timestamps are TIMESTAMPTZ and stored in UTC.
- snake_case naming is used throughout.
- created_at and updated_at are required on mutable business tables; created_by/updated_by are added where actor auditing is meaningful.
- Soft deletion is used only on user/content/business records where recovery or moderation requires it; transactional/history tables are normally immutable.
- Passwords, OTPs and refresh tokens are never stored in plaintext.
- Foreign keys are explicit. Unique constraints prevent duplicate relationships.
- PostgreSQL CHECK constraints should enforce finite status/code values where they are stable; dynamic master data should use master_value references.

## Relationship summary
- user 1:N user_role; role 1:N user_role
- user 1:N refresh_token; user 1:N otp; user 1:N login_history
- user 1:1 user_profile
- user 1:N user_relationship_mode; relationship_mode 1:N user_relationship_mode
- user_profile 1:1 profile_education/profile_career/profile_family/profile_lifestyle/profile_verification/spiritual_profile
- user_profile 1:N profile_photo/profile_language/profile_interest/profile_hobby
- user_profile 1:1 partner_preference; partner_preference 1:N partner_preference_value
- user 1:N profile_view/favorite/saved_search/search_history/recommendation/interest/block/report/notification/subscription
- interest is directed sender→receiver; match represents a mutual relationship and is associated with one relationship mode
- conversation 1:N conversation_participant/message; message 1:N attachment/read/reaction and may self-reference for replies
- plan 1:N subscription; subscription 1:N payment/invoice
- media_file is referenced by profile_photo and message_attachment; media_access grants access to private media
- admin tables reference users and moderated content.

## Important implementation notes
- Do not create separate tables for individual partner-preference attributes. Use partner_preference for scalar/range values and partner_preference_value for multi-select master values.
- Master data should initially cover country, state, city, language, religion, education, occupation/profession, marital status, diet, smoking, drinking, exercise and similar configurable values.
- City/state/country can later be replaced by dedicated geographic tables if geographic scale/query requirements justify it; the current design keeps them in the master-value framework.
- Chat should use WebSocket for delivery and REST for history, conversation listing, pagination and management.
- Recommendation score is a persisted snapshot; the recommendation engine and compatibility logic remain application logic. Relationship mode identifies the user intent/context; it does not select a separate compatibility parameter set.
- Search criteria JSONB is intentionally limited to saved/history snapshots; queryable profile attributes remain relational.
- Before production, privacy/retention rules should determine retention periods for login history, messages, reports and audit data.

## Spiritual profile (v1.1)
The `spiritual_profile` table is a lightweight optional 1:1 extension of `user_profile`.

- `spiritual_community` — optional/nullable
- `spiritual_interests` — optional/nullable
- `practices` — optional/nullable
- `any_spiritual_profession` — optional/nullable
- `dream_spiritual_pilgrimage_destination` — optional/nullable

Do not add spiritual path, role, years of practice, teacher flag, volunteering flag, detailed retreat/pilgrimage history, guru history, or certification history without explicit product/schema approval.

## Compatibility rule
One shared partner-preference/compatibility parameter set is used across DATING, FRIENDSHIP and MARRIAGE. Relationship mode is intent/context; it does not select a different compatibility model.
